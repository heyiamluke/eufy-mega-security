# Project memory

## Current architecture

The Home Assistant integration talks only to the companion gateway over its authenticated local API. The gateway owns the Eufy-specific protocol boundary.

As of v0.1.12, production authentication, device discovery, push-token registration, push normalization, media download, event-image decoding, and first-party PPCS camera streaming use gateway-owned implementations. `eufy-security-client` is not a runtime dependency. The v0.1.24 release work replaces the generic Chromium web-push receiver with a gateway-owned Android FCM/MCS transport, adapted from mega-yfue/eufy-sdk under Apache-2.0; the reference SDK is not a runtime dependency. The unused Web Portal/WebRTC and Thing/SmartLife transport experiments were removed in v0.1.20.

The accepted Mega camera inventory types are 7 (video doorbell), 8 (HomeBase battery camera), 19 (T8160/S330), 23 (T8161/S300 or 3C), 26 (T8162/eufyCam S3 Pro), 31 (T8410/T8410C), 47 (T8425/Floodlight Cam E340), 48 (T8170/SoloCam S340), 63 (T8134/SoloCam C20), 91 (T8213), 94 (T8214/Video Doorbell E340), 104 (T8416/Indoor Cam S350), 151 (Wired Wall Light Cam S100/T84A1), 10005 (T81A0/Solar Wall Light Cam S120), and 10031 (T817L). Types 19, 31, and 91 were identified from privacy-safe v0.1.18 inventory logs; their HomeBase relationship and complete PPCS prerequisites were present. Type 23 was reported in issue #14 with the same HomeBase, channel, PPCS, and DSK prerequisites. Type 63 was reported with the same prerequisites in issue #17, but its events and media have not been verified through this integration. Types 94 and 104 were reported in issue #22 with parent peers, channels, and peer PPCS and DSK prerequisites; discovery, events, snapshots, and live video still need real-device confirmation. Types 26, 47, 48, and 10005 were reported in issue #27 with a T9000 parent, channel, PPCS, and DSK prerequisites. Their discovery, events, snapshots, and live video still need real-device confirmation. HomeBase children route PPCS through their parent. A parentless or self-parented supported camera routes through its own P2P DID, app connection, and DSK key, but a row with a missing non-self parent remains unavailable. HomeBase type 18 is not registered as a camera. From v0.1.21 it is registered separately as a station and owns the alarm, guard-mode, connection, storage, volume, and tone entities. T9000/type 27 remains a PPCS parent for cameras but is not registered as a camera or a managed HomeBase station; its local command protocol has not been verified.

HomeBase availability follows the current authenticated Mega inventory. PPCS connection state is a separate diagnostic because an inventoried HomeBase can be temporarily unreachable on the command channel. The app uses Home Assistant's host network because the local PPCS handshake begins with a UDP LAN broadcast; the gateway API port remains disabled unless a user explicitly maps it. The gateway reads station state through short-lived local PPCS sessions and polls every 60 seconds for recovery, but defers polling while that station is serving camera media. Eufy push events update guard, effective, and siren state without waiting for the poll. Each normalized push emits a copyable summary with device model, numeric event codes, inventory matches, and routing outcome. It omits names, serials, text, and URLs. A Firebase notification that cannot be normalized emits only a payload-free receipt line. Writes are serialized per station, stop active station media, send once, wait for the device acknowledgement, and require a fresh readback before the gateway publishes new state.

The gateway's live transport is now proven directly through Eufy's first-party Mega/PPCS UDP path. The probe obtains station DSK keys and ECC cipher material from Eufy's APIs, performs PPCS lookup/handshake, requests camera video, writes raw H.264, and decodes a first-frame JPEG. It deliberately does not use `eufy-security-client`, the separate SmartLife/Thing login, or an expiring Web Portal Access PIN. A five-camera probe produced H.264 and JPEG bytes for Path, Back door, Doorbell, and Front of House. Garden and Pool completed the PPCS and level-2 handshakes but was out of battery during the no-video probe, so no protocol failure is established. In Home Assistant, the recreated integration exposes five cameras and Path has produced a live image and fresh snapshot. Event sensors and retained event snapshots remain independent of live-stream support.

The Home Assistant app advertises the Supervisor-assigned app hostname discovered from inside the container. This keeps the integration connected across local app rebuilds, repository installs, and restarts without hard-coding a repository-specific slug.

Camera capability discovery begins at the Mega gateway, before Home Assistant presentation. The gateway retains bounded numeric parameter IDs and only the validated current values needed by implemented entities. It evaluates each device against the [camera capability lookup](../CAMERA_CAPABILITY_MATRIX.md) through the authenticated `/api/camera-capabilities` endpoint. The lookup contains seven camera media/event paths and four implemented battery reads. No reference SDK is a runtime dependency. Battery level, the charging bitfield, health, and temperature refresh from Mega inventory every 60 seconds. Home Assistant creates only the battery entities backed by parameters that camera reports. Known mains models with sentinel battery data do not advertise them. Startup logs privacy-safe model groups. An unfamiliar type needs two camera-specific media parameters and a ready route to be flagged for review, but the camera allowlist remains the admission gate.

The same Mega-first boundary records [sensor, HomeBase, and doorbell baselines](../DEVICE_CAPABILITY_BASELINES.md) through `/api/device-capabilities`. One core definition file per family feeds a shared `device-capabilities-core.ts` evaluator. Camera admission, media-route evidence, and mains battery sentinels remain explicit family rules. Standalone sensors now have a separate normalized `/api/sensors` state. Reported contact, battery, and last-seen fields create matching entities, while recognized PIR types get a transient motion entity. Contact push code 3 carries open or closed state and PIR push code 14 triggers motion. T8010 is a read-only discovered HomeBase with a child-camera route diagnostic; T8030 alone receives verified station controls, and T9000 remains a station peer without a managed security entity.

Capability startup logs show the Home Assistant adapter and known-type admission decision beside reported core evidence, unimplemented reads, route readiness, and offerable gateway paths. Camera media readiness uses DSK keys retrieved for the current inventory pass, not a stale pre-refresh key set. Unknown camera-like rows remain review candidates only. Standalone sensor fields require matching parameter or device-type evidence before the sensor adapter exposes them. Unverified station command protocols cannot inherit the HomeBase 3 controls. Capability shape alone does not automatically admit a new device type.

## Delivery state

v0.1.33 treats an authenticated HTTP 404 from the push-thumbnail path as temporary cloud propagation for a bounded three-attempt window. The retry remains inside the original per-camera snapshot queue, so duplicate style-3 notification deliveries stay suppressed without losing the later image. A privacy-safe success log confirms when the resulting JPEG is retained.

v0.1.32 restores the Home Assistant app's release history by backfilling its app-facing changelog for v0.1.27 through v0.1.31. The release consistency check now requires the current version heading in both the repository changelog and `eufy_event_gateway/CHANGELOG.md`, preventing future app releases from silently publishing stale notes.

v0.1.31 expands the camera push vocabulary into distinct motion, person, stranger, pet, vehicle, dog, crying, sound, and stranded-package events. Attributed push thumbnails are retained independently of event classification. Temporary Eufy media requests use the active Mega token and user token only on the allowlisted Eufy host, then follow one allowlisted object-store redirect without forwarding credentials. Duplicate follow-up deliveries are suppressed by Eufy's event id. Repeated HomeBase recovery failures are summarized, with a separate recovery log when polling succeeds again.

T8030 station writes remain serialized and are never retried. If a write acknowledgement times out, the gateway now performs the already-required fresh readback: matching state confirms success, while mismatched or failed readback still returns an error. Explicit command rejection is never converted to success. Privacy-safe logs distinguish readback-confirmed missing acknowledgements from failed commands, and the Home Assistant client surfaces the gateway's bounded error text instead of only the HTTP status.

T817L is a USB-C-powered camera, not a battery camera. Its Mega inventory nevertheless reports battery level, charging, and temperature parameter IDs. Those values are compatibility sentinels: the shared mains-sentinel classification suppresses them in capability diagnostics and normalized camera state, while Home Assistant removes the exact battery entity IDs created by v0.1.28 on the next integration setup. Camera admission, HomeBase routing, events, snapshots, and live video remain unchanged.

The `mscodemonkey/refresh-snapshot-after-stream` branch rotates Home Assistant's camera image token when a completed live session has left a newer retained JPEG. The gateway already extracts and persists frames throughout a stream; the missing token rotation allowed Home Assistant's camera proxy URL to keep displaying the pre-stream image. Home Assistant's native camera dialog does not provide integrations with a slot for custom startup overlay or caption text, so a "Please wait" message would require an upstream frontend change or a custom dashboard card rather than a backend entity attribute.

v0.1.28 implements the first Home Assistant entity slice from the v0.1.27 capability definitions. It adds camera and doorbell battery entities, a normalized standalone-sensor API, contact/PIR binary sensors, standalone battery percentage, and last-seen time. Mega inventory values refresh every 60 seconds and push events update contact or motion immediately. The simulated gateway API, SSE stream, automated gateway tests, TypeScript build, Python compilation, and hassfest validation passed before release. Real standalone-sensor hardware verification remains outstanding.

v0.1.27 publishes Mega-first core capability evaluation for camera, doorbell, HomeBase 3, and sensor inventory rows, with privacy-safe startup groups and authenticated inspection endpoints. Camera media route readiness uses DSK keys from the current inventory pass. The gateway still admits cameras through known type allowlists. Battery values, standalone sensor state, and unfamiliar camera types need separate implementation and hardware verification before Home Assistant can expose them or admit them automatically.

The v0.1.26 release work packages the issue #28 camera-timeout rejection fix and the issue #27 admission of T8162/type 26, T8425/type 47, T8170/type 48, and T81A0/type 10005 through the existing inventoried parent-peer route. A frame or clip timeout during slow PPCS startup now reaches its caller instead of exiting the gateway as an unhandled rejection. The reporter's T9000/type 27 provides the camera PPCS connection and DSK key, but it is not a camera or managed station. The release does not add T9000 security or settings entities because the existing controls assume the T8030 command protocol. The affected installation still needs to confirm crash-loop recovery, camera discovery, push events, snapshots, and live video.

v0.1.25 packages the merged issue #22 T8214/type 94 and T8416/type 104 camera admission. Both use the existing inventoried parent-peer route; T8214 also exposes the existing doorbell-press sensor. The T8023/type 25 MiniBase Chime is the doorbell's inventoried PPCS peer, while the T8030/type 18 HomeBase is the indoor camera's peer. Neither is added to the camera inventory. The reported `push_unparsed` notification does not affect discovery. Hardware verification remains outstanding.

v0.1.23 admits Mega type 23 / T8161 through the existing HomeBase camera path. The reporter's inventory had the station, channel, PPCS, and DSK prerequisites; real Home Assistant discovery, events, snapshots, and live video still need that device result. This support was not part of the published v0.1.22 tag.

v0.1.22 packages the merged HomeBase 3 support, Mega type 63 / SoloCam C20 admission, type 151 / S100 direct PPCS route, privacy-safe per-push diagnostics, host-network configuration, and HomeBase storage unit and display fixes.

The S100 type 151 and direct PPCS route are merged for community testing. Real S100 verification of discovery, live video, snapshots, and events remains outstanding; the device must not be marked tested yet. SoloCam C20 type 63 also needs hardware testing for discovery, events, snapshots, and live video.

The issue #8 logging in v0.1.22 adds privacy-safe per-push summaries so a HomeBase 2/T8210 report can show whether doorbell and motion notifications reach the gateway and whether the current detection rules handle them. It does not claim HomeBase 2 media or push behaviour is fixed.

The issue #17 type 63 / T8134 admission in v0.1.22 registers the SoloCam C20 as a camera. The reporter's inventory shows its HomeBase parent, camera channel, PPCS identity, and station DSK readiness. That evidence supports discovery and stream eligibility, not a claim that event sensors, snapshots, or live video work yet. Hardware confirmation is required before marking SoloCam C20 tested.

The v0.1.24 issue #8 work follows local testing that showed the generic Firebase receiver registered as a Chromium web-push application and delivered metadata-only messages while the owner phone received camera alerts. Extracting its MCS appData did not recover the camera payload. The Android registration flow in mega-yfue/eufy-sdk uses the current Eufy app package, certificate, and FCM sender instead. The gateway now owns that Android FCM/MCS transport and registers its token with Mega using an empty `voip_token`, matching the app request. The old generic receiver is no longer a runtime dependency.

The standalone `debug:push` probe runs the production Mega and push boundary without Home Assistant or PPCS. On a local guest account it received a T8113-Z motion payload (`3101`), T817L person payload (`3102`), and T8210 doorbell press payload (`3103`), then routed them as motion, person, and doorbell press. A restart reused the saved Android identity without replaying old messages. Doorbell press now has a transient gateway state flag and a Home Assistant binary sensor on supported doorbells. Live Home Assistant entity behaviour remains a separate installation check; the local hardware proof establishes payload delivery and gateway routing.

v0.1.21 adds the first HomeBase 3 entity set and gateway control path. The automated gateway suite covers inventory normalization, station-state immutability, push normalization, privacy filtering, and HomeBase camera-info and storage parsing. Local hardware confirmation is still required for command framing, storage units and status meanings, all writable value ranges, and the exact siren stop codes before release. The integration does not expose manual siren activation.

v0.1.20 removes the retired Web Portal/WebRTC, Thing/MQTT, and experimental native-relay modules and their dependencies. Saved Mega sessions now use a version 2 `scrypt` credential verifier; older credentials and tokens are rejected and require one fresh Eufy sign-in after upgrading, while the non-secret device identifier is retained. The PPCS session still creates an ephemeral RSA-1024 key because observed cameras return the encrypted video key in a fixed 128-byte protocol field. That compatibility risk remains documented until real hardware proves a larger modulus works.

v0.1.19 adds camera inventory types 19, 31, and 91 after v0.1.18 support logs identified the T8160/S330, T8410/T8410C, and T8213 rows that an affected installation received from Mega. The reporter then confirmed that all five cameras were discovered with sensor entities, retained images, and live streams working through an S380/T8030 HomeBase. Type 18 remains excluded as the HomeBase parent.

v0.1.18 makes copied support logs self-identifying. Every gateway-owned line carries a UTC timestamp, severity, release version, per-process run ID, component, and stable event name. Explicit start, listening, stop, and fatal events reveal restart boundaries; expected readiness-probe failures are suppressed. Grouped inventory lines expose model, type, category, acceptance, station, and stream-readiness decisions without device names or serial numbers. The logging boundary accepts only human-readable messages, redacts common credentials and account email addresses, and keeps stack frames attached to the same version and run without logging raw provider objects.

v0.1.17 shows the empty verification-code field directly in app configuration without an optional-field toggle. After the provider connects, cameras without a retained image receive sequential first-run snapshot captures; sleeping or failed cameras do not block the remaining queue and remain eligible on a later startup. The app entrypoint traps Supervisor termination, waits for the gateway process, and exits successfully so an intentional stop is not reported as exit code 143.

v0.1.16 fixes first-sign-in email verification across the app restart documented for the configuration-field fallback. The gateway persists Eufy's limited pre-verification Mega session before returning the challenge, then submits the code with that same token after restart. The Web UI also routes email verification through the active Mega client rather than the separate legacy web session.

v0.1.15 adds the first-day developer guide, the detailed Mega platform reference, and the file-level source/test documentation needed for outside testers and contributors. The public and app READMEs link directly to those documents. This release does not change the runtime protocol path.

v0.1.13 renames the user-facing project, Home Assistant integration, and HACS repository to Eufy Mega Security while preserving the internal `eufy_event_gateway` domain, service namespace, app slug, and discovery service for existing installations. Those internal identifiers are intentional compatibility names, not stale user-facing branding.

v0.1.12 adds the gateway-only first-party PPCS proof and wires that transport into on-demand camera streaming. An existing valid Mega session was migrated once from the previous client state, then saved in the gateway-owned session format. New Mega authentication supports email verification and the app's CAPTCHA interface when Eufy requires either challenge. The separate web transport present in that release was retired in v0.1.20.

Never log or expose credentials, session tokens, signing identities, raw signed media URLs, complete push payloads, or device serial numbers in diagnostics.
